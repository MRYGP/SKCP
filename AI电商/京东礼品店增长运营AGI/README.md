# 跨平台小商家经营状态层 · 项目入口

## 当前定位

本项目早期名称为“京东礼品店增长运营 AGI”。最新定位分两层：

1. 现实滩头：为多平台经营的小商家建立一层统一经营状态层，把京东、淘宝、天猫、拼多多、抖音、微信、线下和表格里的割裂经营事实，翻译成可审核的经营判断和下一步动作。
2. MUSK 终局：从“帮卖家经营平台店”升级为“企业礼品采购 Agent 网络”，让企业采购需求和礼品供给能力绕过平台流量地主，直接完成匹配、报价、确认、履约和复购。

京东朋友店是第一块试验田，不是最终边界。

## 当前最重要的一步

不要继续先写宏大方案。先拿朋友店做第一轮采集，输出五件东西：

1. 全渠道经营地图；
2. 三个真实数据割裂点；
3. 第一版统一经营状态表；
4. 三个企业采购 / 批量定制需求样本；
5. 这周能执行的 3 个动作。

## Go / Kill

Go 信号：

- 朋友店存在至少 2 个单平台后台看不到、但影响经营动作的跨渠道问题；
- 店主看到统一经营表后，能发现过去没看清的问题；
- 至少 1 个动作来自跨渠道视角，而不是普通京东后台优化；
- 朋友店存在企业采购、批量定制或可复购客户链路；
- 店主愿意继续提供数据或愿意付费换持续经营动作。

Kill / 调整信号：

- 朋友店完全单平台，无私域、无线下、无其他渠道，且无明显数据割裂；
- 统一经营表只带来看板爽感，不能导出动作；
- 企业采购/批量定制需求不存在，项目只能退回普通零售运营；
- 店主真实痛点仍是“不会做京东后台动作”，而不是跨平台经营割裂或采购需求匹配；
- 采集成本过高，第一版就滑向重 ERP。

## 项目纪律

- 不把“跨平台”写成口号，必须落到具体经营损失。
- 不把“MUSK 模式”写成宏大叙事，必须落到一次企业采购任务样本。
- 不做大 ERP，先做最小统一经营状态表和采购任务表。
- 不承诺自动出单。
- 不接管平台账号。
- 每个功能都必须能回答：它是否沉淀同一份经营状态层？是否能交付可审核结果？是否让平台外连接更可行？
